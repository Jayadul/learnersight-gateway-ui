SendText Integration Guide

Single endpoint for dispatching SMS, WhatsApp and Voice messages, with automatic fallback when a delivery fails. Share this page with any third-party application that will integrate.

Endpoint

POST GET {{ baseUrl }}/sendtext
Content-TypePOST: application/x-www-form-urlencoded or application/json — both are accepted with the same fields. GET: same fields as query-string params — use it only where the integrator's platform cannot easily do POST, since POST keeps credentials off the URL
Authenticationapikey + secretkey (issued by Net ZerO). Invalid or missing credentials are rejected
ProcessingAsynchronous. The response confirms queuing, not delivery
GatewaysEach channel type may have several gateways configured. Every tag names the one it uses by label — only an untagged message falls back to a default
PacingA WhatsApp gateway may be given a send delay to stay under provider rate limits, so its deliveries arrive spaced out rather than all at once. A long recipient list takes proportionally longer

Request Parameters (form fields, JSON body keys, or the same names as query params on GET — identical either way)

FieldRequiredDescription
toUser Required Recipient number(s) with country code, e.g. 8801700000001. For multiple recipients, separate with commas: 8801700000001,8801700000002. Every number receives every tagged message.
messageContent Required The message. Use channel tags (below) to pick channels. Without any tag the whole content is sent as a plain SMS.
apikey Required API key issued by Net ZerO. Requests with a wrong or missing key are rejected.
secretkey Required Secret key issued by Net ZerO. Keep it confidential. Use it server-side only, never in client-side code.
callerID Required Sender ID recorded with the request.

Channel Tags

Compose messageContent from one or more [tag::content] blocks. Each tag creates one delivery, and several tags may be combined in a single request. There are three channels — SMS, WhatsApp and Voice.

Every tag names its gateway. A tag is type:label, where label is the slug of the gateway that should carry it — for example [sms:revemain::…]. The labels configured for this installation are listed below. Sending no tag at all is the one exception: that goes out as a plain SMS on the default SMS gateway.

TagChannelExample
[sms:LABEL::TEXT] SMS [sms:revemain::Your OTP is 123456]
[wp:LABEL::TEXT] WhatsApp [wp:waprimary::Your appointment is confirmed.]
[wp:LABEL::TEXT||URL] WhatsApp with media — the same tag; the URL is what makes it a media message [wp:waprimary::See invoice||https://example.com/invoice.pdf]
[sms:LABEL-wp:LABEL::TEXT] SMS and WhatsApp (same text, two deliveries, one gateway named per leg). Media works here too: append ||URL and it goes on the WhatsApp leg [sms:revemain-wp:waprimary::Big sale this weekend!]
[call:LABEL::CAMPAIGN_ID||LOT] Voice call — the campaign to dial, then the lot within it [call:voicemain::due-bill-api||1]
[template:LABEL::TEMPLATE_NAME||VAR1||VAR2] WhatsApp Template — a Meta pre-approved template, variables in order. Must name a template already registered on that channel under Channels, with the exact same number of variables it was registered with. Text only (no media); not combinable with another tag; never falls back. [template:watemplate::order_confirmation||Jane Doe||ORD-123]
(no tag) Plain SMS with the full content, on the default SMS gateway Hello without any tag

|| means the same thing everywhere: it separates a media URL from its caption, and a lot number from its campaign id. Labels are lowercase letters and digits only. Tags are case-insensitive.

Automatic Fallback

If a delivery fails at the provider, Net ZerO can retry it on another channel. Which retries happen is configured by Net ZerO, not by the request — three rules decide whether one applies:

Same type by default A failed WhatsApp send retries on another WhatsApp channel, SMS on another SMS, Voice on another Voice. Retrying across types changes both the delivery format and the per-message cost, so it has to be enabled deliberately.
One tag only A request that asks for more than one delivery never gets a fallback — for example [sms:a::…][wp:b::…] or any [sms:a-wp:b::…] combined tag. The second channel is already the redundancy, so no third message is generated and nothing extra is charged.
Visible either way A retry appears in Message Logs as an extra delivery badged Fallback. When a retry is skipped, the message detail says so.

Balance Lookup (read-only, no credentials)

GET {{ baseUrl }}/balance?callerID=yourlabel

A separate, unauthenticated endpoint for checking a gateway's remaining credit — currently SMS labels only. Calls the provider live on every request; a failed live read falls back to the last known cached figure rather than an error. Returns {{ '{' }} "label", "balance", "creditLimit", "lastCheckedAt" {{ '}' }}, or a 404 with {{ '{' }} "status": "error", "message" {{ '}' }} for an unknown label, an inactive channel, or a channel type with no balance.

No apikey/secretkey required — the label alone is enough, and it triggers a real provider call each time. Deliberate trade-offs: anyone who can guess or learn a label can read its balance, with no rate limit on how often they can ask.
